## P2 (fix before merge)

1. **`Screens/Player/PlayerAspectMode.swift:67` (`AspectWriteback.valueToPersist`) + `Screens/MPVPlayerView.swift:2224` (`persistAspectIfNeeded`)**: round 1's scenario is fixed only when the user presses faster than the 2 s flash. Someone looking at each mode before deciding (the normal way to judge a fit, and the reason the first run of the aspect leg read `aw=3`) goes Fit, Fill (looks 3 s: Fill is written), Zoom (looks 3 s: Zoom is written), Stretch (rests: nothing is written). The profile, the next playback and the phone are left on Zoom, the mode the user rejected by moving on. Round 1's fix asked for Stretch to leave the session-start value; the code leaves the last intermediate write instead. The plan's device-pass item says "quickly", so the pass would not catch it. **Fix:** keep `aspectSessionStart` (set at FILE_LOADED, moved by the settings watcher only when the change did not come from our own write); when the resting mode is Stretch, persist `aspectSessionStart` if `aspectPersisted` differs from it. Simpler alternative: persist only in `viewWillDisappear` when `isLeavingPlayer` (and on the flash only for non-Stretch modes), with Stretch mapping to the session-start value. Add a pure test: fit, fill (persisted), zoom (persisted), stretch at rest persists fit.

## P3 (nice to have)

2. `Screens/Player/HarvestCrashSentinel.swift:35` (`checkAtLaunch`, called from `MPVPlayerView.swift:460`): the check runs at every player `viewDidLoad`, not once per process, and the flag carries no owner. When a new mpv controller loads while the previous one is still alive and inside a capture (next-episode autoplay while the old file is playing, a quick Replay or relaunch of the player), the new controller reads the old one's live flag as a crash and turns the harvest off on that Apple TV until someone finds the Developer row. Rare (capture time over the 10 s interval, under 1 %) but silent and sticky. **Fix:** arm with a per-process token (a launch UUID string or pid plus process start time) instead of `true`, and treat the flag as a crash only when its token is not this process's. Related, smaller: only a file's first capture is synchronised to cfprefsd, so a crash on a later capture (a resolution or HDR change mid-file) can lose the armed write; arming with a token per capture plus the same first-capture sync is enough for the deterministic case the sentinel targets, so note it rather than add a sync per capture.

3. `iosApp/NuvioTVUITests/PlayerTransportUITests.swift:593`: the three return presses rely on each `remote.press` plus 0.5 s staying under the 2 s flash. On a slow simulator run (a press that takes over 1.5 s) a flash clears mid-cycle and the leg fails with `aw=3`, the same symptom its first run hit, so it can flake. **Fix:** a DEBUG launch argument for the flash length (`-debug.aspectFlashSec 6`) used by this leg, or assert the write count from the `[Aspect] persist` log lines filtered to resting modes. Related, `:351`: reading `livePos` before the clock moves the one-read bias to the other side rather than removing it; taking the clock before and after the read and using the midpoint makes the 2.5 s tolerance honest.

4. `Screens/Player/PlayerChaptersTab.swift:35`: the default-focus claim is untested (the fixture's current chapter is row 0, so the leg passes whether or not `.defaultFocus` works). **Fix:** in the Chapters leg, seek to the fourth chapter, open the tab, and assert the focused row id is `player.panel.chapter.3`; keep "a long list opens on the ticked chapter" on the device pass.

5. `Screens/Player/PlayerChapters.swift:72` + `Screens/MPVPlayerView.swift:1661`: trimming is one-way. A file whose duration starts as an estimate and grows (a progressive download without an index, an event playlist) drops its late chapters for good once they fall inside the slack of the early duration. Harmless for normal files. **Fix if it matters:** keep the untrimmed list on the controller and derive the published list from it whenever the duration changes.
