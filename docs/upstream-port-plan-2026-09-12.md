## Three action items this run — most substantive batch since the 2026-08-31 batch

### [HIGH, likely live] `1854dfc3` "fix(sync): prevent automatic pulls from restoring deleted data"

Upstream found and fixed a real class of bug: a fresh pull that legitimately returns an empty server-side collection (addons, library items) was being treated by the client as "the server must be wrong, restore from local storage" — which silently resurrects data the user actually deleted (or migrates stale local-only data back up to the server). The fix removes that local-fallback/migration logic from `AddonRepository.pullFromServer()` and `LibrarySyncReconciler.reconcileLibrarySnapshot()` (`preserveLegacyLocalWhenServerEmpty`/`migrateLegacyLocalItems` deleted outright), and separately hardens `ProviderCredentialSync`/`ProfileSettingsSync` against a profile-switch race: switching profiles could let a stale-signature push land against the just-switched-to profile's credentials before its own baseline snapshot was captured (`ProfileRepository.onProfileChanged()` now calls a new `ProviderCredentialSync.onProfileChanged()`/`ProfileSettingsSync.onProfileChanged()` to re-baseline immediately; the push-debounce pipeline gained a `distinctUntilChanged()`-before-`drop(1)` reorder plus a freshness re-check right before firing; `ProviderCredentialModels.mergeRemote()` now lowercases the remote-side provider match too, and blanks a credential's local value instead of leaving stale data in place when the remote copy is missing it).

**Confirmed unported, and confirmed still exhibiting the pre-fix pattern verbatim in `shared/`:**
- `shared/src/commonMain/kotlin/com/nuvio/app/features/addons/AddonRepository.kt` — `pulledFromServer`, "migrating local addons to server", "preserving local addons" all present exactly as upstream just deleted.
- `shared/src/commonMain/kotlin/com/nuvio/app/features/library/LibrarySyncReconciler.kt` + `LibraryLocalState.kt` — `preserveLegacyLocalWhenServerEmpty`/`migrateLegacyLocalItems` present exactly as upstream just deleted.
- `shared/src/commonMain/kotlin/com/nuvio/app/core/sync/ProviderCredentialSync.kt` + `ProviderCredentialModels.kt` — `pendingScopes`, `shouldSeedProviderCredentials` still present (upstream deleted these as part of simplifying the push/pull interleaving); no `onProfileChanged()`.
- `shared/src/commonMain/kotlin/com/nuvio/app/core/sync/ProfileSettingsSync.kt` — no `onProfileChanged()`; still `.drop(1).distinctUntilChanged()` in that order, not the corrected `.distinctUntilChanged().drop(1)`.
- `shared/src/commonMain/kotlin/com/nuvio/app/features/profiles/ProfileRepository.kt` — `onProfileChanged`-fan-out block has no `ProfileSettingsSync.onProfileChanged()` call.

**This is not a mechanical port.** The fork's `shared/` copies of `ProviderCredentialSync.kt`/`ProfileSettingsSync.kt` in particular have diverged heavily beyond upstream since the 2026-08-24 sync-reliability batch (extra Codex-round hardening, `bootstrap.initialized`/`shouldBlockUnhydratedAddonPush` gating on `AddonRepository`'s `pulledFromServer` flag that upstream's diff doesn't know about). Porting needs a line-by-line reconciliation, not a blind copy — in particular, decide whether `AddonRepository`'s `pulledFromServer` flag can be fully removed (upstream's intent) without breaking the fork-only `shouldBlockUnhydratedAddonPush` hydration gate that reads it. Given the fork's history of paying for exactly this class of bug before (addon-removal + Simkl cross-reference deltas, the 2026-08-24 batch, BUG-75), this is worth prioritizing. Suggested approach: port the `LibrarySyncReconciler`/`LibraryLocalState` half first (smallest, most self-contained — no fork-only flags to reconcile), then tackle `AddonRepository` (needs the `pulledFromServer` reconciliation), then `ProviderCredentialSync`/`ProfileSettingsSync`/`ProfileRepository.onProfileChanged()` as a group (needs care around `pendingScopes` removal and the fork's own retry/backoff additions). Add/port upstream's own regression coverage in the diff (`PluginSyncTest.kt` is misnamed but is actually the sync test file for this fix; `ProviderCredentialModelsTest.kt` and `LibrarySyncReconcilerTest.kt` got new cases too — mirror those into `shared/commonTest`).

### [MEDIUM/LOW, investigate before porting] `2e244028` + `5cacbe6e` — plugin runtime "match TV" perf batch

Two same-evening commits from the same author, both titled "matching TV": `2e244028` "perf(plugins): match TV QuickJS pool, bytecode cache, and fetch cancel" (bounds scraper execution to a background thread pool instead of unbounded `Dispatchers.Default`, caches the compiled polyfill/settings-call bytecode instead of recompiling per-invocation, propagates coroutine cancellation into the underlying OkHttp call, caps the DOM parse cache) and `5cacbe6e` "fix(plugins): pause local plugin search during playback" (adds `PluginRepository.setLocalPluginSearchPaused()`, wired so entering the player pauses local JS-scraper searches and leaving/opening the sources panel resumes them, "matching TV"). Both commits are scoped entirely to `composeApp/` (mobile's Compose player + Compose plugin runtime) — `2d03b258` "fix(plugins): restore iOS runtime compilation" is a same-batch composeApp-only compile fixup for `2e244028` and is only relevant if that commit gets ported.

The "matching TV" phrasing implies these optimizations already exist somewhere upstream calls "TV" — but a direct comparison shows **tvOS's own parallel implementation does not have them**: `shared/src/tvosMain/kotlin/com/nuvio/app/features/plugins/runtime/PluginRuntime.kt` is a byte-identical copy of composeApp's *pre-fix* `fullCommonMain/.../PluginRuntime.kt` (same `com.dokar.quickjs` imports, same unbounded `withContext(Dispatchers.Default)`, same recompile-per-call, no bytecode cache), and `shared/.../features/streams/StreamsRepository.kt` / `shared/.../features/player/PlayerStreamsRepository.kt` have no `setLocalPluginSearchPaused`/`pauseSearchForPlayback` equivalent. So either "TV" refers to an Android-TV-flavored build inside upstream's own monorepo that isn't visible from this fork's history (most likely, given the phrasing), or this really is a gap in our fork too. Recommend investigating before committing to a port: (1) confirm whether tvOS's native player (`MPVPlayerView.swift`/`NativePlayerScreen.swift`) actually triggers local-scraper JS execution while video is playing (e.g. via next-episode preloading or a credential-refresh retry) in a way that would contend for CPU/QuickJS runtime — if not, the pause/resume feature has no live bug to fix on tvOS; (2) if tvOS's on-device scraper runs do show jank or slow bytecode-recompile overhead on weaker Apple TV hardware, the pool/bytecode-cache/fetch-cancel pattern from `2e244028` is portable to `shared/tvosMain` (adapt to Swift/`Dispatchers.IO`-equivalent rather than Android's `Executors.newFixedThreadPool`, mirror the `Semaphore`-bounded `PluginRuntime.executePlugin`, cache `JsRuntime.polyfillBytecode`/`settingsCallBytecode`). Not urgent; no user report of scraper-related jank on tvOS to date.
