### 1. [MEDIUM/HIGH, needs Christian's call — not mechanical] Bundle a default TMDB API key (`60ee0160` "fix(tmdb): use bundled API key")

Upstream removes the requirement that users supply their own TMDB API key. `TmdbService.ensureTmdbId()`/`tmdbToImdb()` now read a compile-time `TmdbConfig.API_KEY` constant instead of `TmdbSettingsRepository.snapshot().apiKey`; `TmdbSettings.apiKey`/`hasApiKey` are deleted; `TmdbSettingsRepository.setApiKey()`/`TmdbSettingsStorage.loadApiKey()`/`saveApiKey()` are deleted; TMDB is removed entirely from the credential-sync path (`ProviderCredentialIds.TMDB` constant deleted, `ProviderCredentialSync.kt`'s snapshot/apply/`ensureRepositoriesLoaded()` all drop their TMDB branches, `ProfileSettingsCredentialPolicy.kt` special-cases TMDB to never merge remote credentials). The bundled key itself is generated at build time: `composeApp/build.gradle.kts`'s existing `GenerateRuntimeConfigsTask` gained a `tmdbApiKey` input (sourced from a `TMDB_API_KEY` gradle/env property, the same mechanism already used for `NUVIO_SUPABASE_ANON_KEY`/`SENTRY_DSN`) and now writes `TmdbConfig.kt` instead of deleting it.

**Confirmed unported and confirmed a live UX pain point on tvOS**, not just an unported diff: `shared/.../tmdb/TmdbSettings.kt` still has `apiKey`/`hasApiKey`; `shared/.../tmdb/TmdbSettingsRepository.kt`/`TmdbSettingsStorage.kt`/`TmdbService.kt` all still have the pre-fix user-key path; `shared/.../core/sync/ProviderCredentialModels.kt`/`ProviderCredentialSync.kt` still carry `ProviderCredentialIds.TMDB`. On tvOS, `iosApp/NuvioTV/Screens/SettingsViewModel.swift` has a live "enter your TMDB API key" flow (`tmdbHasKey`, `TmdbSettingsRepository.shared.setApiKey(value:)`, a clear-key path) — typing an API key with the Apple TV remote's on-screen keyboard is exactly the kind of 10-foot friction this fix would eliminate, so this is a genuine UX win for tvOS, not just an upstream-parity item.

**Why this is not mechanical, and not something to build unattended:**
- `shared/.../core/sync/ProviderCredentialSync.kt` is the same file the 2026-09-12 daily check already flagged as heavily diverged from upstream (fork-only `pendingScopes`/`shouldSeedProviderCredentials`/`bootstrap.initialized` gating layered on top since the 2026-08-24 sync-reliability batch) — that reconciliation is still owed (see "Carried open items" below) and this commit's TMDB-removal hunks land in the exact same object, so the two should be reconciled together, in one pass, not as two separate edits to a fragile file.
- The bundled key needs an actual secret. `shared/build.gradle.kts` already has the parallel machinery for this — `GenerateSharedRuntimeConfigsTask` already generates `SupabaseConfig.kt` into `shared/` from a gradle/env property, so the plumbing pattern to copy is proven — but **the TMDB API key value itself is Christian's call**: reuse the same key upstream bundles (unknown/unverifiable from here — it lives in NuvioMedia's CI secrets, not the public repo), provision Nuvio's own TMDB key, or decide the product should keep asking users for their own key. Do not guess.
- Once a key is decided, the port is: mirror `GenerateSharedRuntimeConfigsTask`'s `SupabaseConfig.kt` pattern into a new `TmdbConfig.kt` generator in `shared/build.gradle.kts`; update `shared/.../tmdb/TmdbService.kt`/`TmdbSettings.kt`/`TmdbSettingsRepository.kt`/`TmdbSettingsStorage.kt` to drop the user-key path (upstream's diff is a clean template); remove TMDB from the three credential-sync files as part of the same reconciliation pass; then strip the "TMDB API Key" entry row and `tmdbHasKey`/`setApiKey`/clear-key calls from `SettingsViewModel.swift` and whatever SwiftUI row renders it.
